## 摘要
检索增强生成（RAG）为大语言模型访问外部知识提供了一种有效途径。然而，现有方法依赖于密集相似度检索，在处理结构化约束和多跳推理时存在固有限制。融入知识图谱可部分缓解这些问题，但代价是语义碎片化、维护开销高以及增量更新困难。本文提出 SAG（SQL 检索增强生成），一种面向检索和智能体系统的结构化架构。SAG 并非预先构建全局静态图，而是将每个文本块转换为一个语义完整的事件和一组索引实体，然后利用 SQL 联接查询动态地将共享实体的事件链接成局部超边，在查询时构建一个动态实例化的局部索引结构。这种设计避免了对全局图重建和持续维护的需求；系统通过依赖标准数据库基础设施，天然支持增量写入、并发处理和持续扩展。在 HotpotQA、2WikiMultiHop 和 MuSiQue 这三个标准多跳基准测试中，SAG 在 9 个 Recall@K 指标中的 8 个上取得了最佳结果，在要求最高多跳推理能力的 MuSiQue 上达到了 80.0% 的 Recall@5。SAG 也已部署到数亿数据项的生产规模中，在线检索延迟保持在秒级以内。项目网站和代码见 https://github.com/Zleap-AI/SAG-Benchmark。

## Abstract
Retrieval-Augmented Generation (RAG) offers an effective approach for large language models to access external knowledge. However, existing methods rely on dense similarity retrieval and face inherent limitations in handling structured constraints and multi-hop reasoning. Incorporating knowledge graphs partially alleviates these issues, but at the cost of semantic fragmentation, high maintenance overhead, and difficult incremental updates. This paper introduces SAG (SQLRetrieval Augmented Generation), a structured architecture for retrieval and agent systems. Instead of pre-building a global static graph, SAG converts each chunk into one semantically complete event and a set of indexing entities, then uses SQL join queries to dynamically link events that share entities into local hyperedges,constructing, at query time, a dynamically instantiated local index structure. This design avoids the need for global graph rebuilding and ongoing maintenance; the system naturally supports incremental writes, concurrent processing, and continuous scaling through its reliance on standard database infrastructure. Across HotpotQA, 2WikiMultiHop, and MuSiQue, three standard multi-hop benchmarks,SAG achieves the best results on 8 out of 9 Recall@K metrics, reaching 80.0% Recall@5 on MuSiQue, the benchmark with the highest multi-hop reasoning demands.SAG has also been deployed at a production scale of hundreds of millions of data items, with online retrieval latency kept within seconds. Project site and code are available at https://github.com/Zleap-AI/SAG-Benchmark.

## 1. 研究动机与核心问题
- **背景**：大语言模型驱动的智能体系统需要在海量、持续增长的数据中进行多步关联查询，而传统检索增强生成（RAG）存在明显短板。
- **现有方法的局限**：
  - **密集向量检索（NaiveRAG）**：仅依赖语义相似度匹配，难以捕捉显式的实体关联链，面对多跳推理、时间约束或角色关系时效果骤降。
  - **图增强检索（GraphRAG）**：虽然通过离线构建知识图谱来描述实体关系，但面临三重提取和实体对齐引入的累积误差、高昂的构建与维护成本，且查询时常退化为节点级相似度匹配，导致“离线结构与在线召回脱节”。
- **论文目标**：提出一种无需预建全局静态图、能够在查询时动态组织结构化证据的检索架构，平衡检索质量、结构能力和系统开销。

## 2. 方法论核心思想与技术细节
### 2.1 总体思路
SAG 用 **SQL 引擎** 承担结构化过滤与连接，**向量引擎** 负责语义扩展，**大语言模型** 仅用于最终的高价值选择任务。其核心不是替换 RAG 的各个模块，而是重新分配检索管线中的职责。

### 2.2 离线阶段：事件 - 实体索引构建
- **事件（Event）**：每个文档块被 LLM 压缩为一个语义完整的陈述句（一事件一块），保留整体语义，避免三元组拆解带来的语义碎片化。
- **实体（Entity）**：从同一块中抽取 **11 种类型** 的实体（时间、地点、人物、组织等），仅作为索引和桥接点，不承载完整语义。
- **存储**：事件与实体以多对多关系写入 SQL 数据库，并同步建立向量索引和全文索引。

### 2.3 在线阶段：三步骤检索
1. **种子检索（Seed Retrieval）**：
   - **路径A（实体导向）**：LLM 从查询中提取种子实体，通过实体向量索引扩展语义相近的别名实体，再利用 SQL 连接精确召回所有关联的事件。
   - **路径B（事件导向）**：直接用查询向量在事件索引中做相似度检索。
   - 合并两路结果得到初始候选事件集 \(E_R\)。

2. **查询时动态扩展与选择**：
   - **超边激活**：以 \(E_R\) 为起点，利用 SQL 反向连接获取新关联的实体（“实体前沿”），再以此为桥接点发现更多事件，逐跳扩展候选池。该过程完全由 SQL 连接驱动，而非图传播算法。
   - **粗排与最终选择**：按向量相似度截断候选事件（默认 top-100），然后：
     - **结构路径**：由 LLM 对候选事件精排，选出顶部 \(K_{\text{event}}\) 个事件并映射回原始块。
     - **语义路径**：直接用查询向量从块索引中召回 \(K_{\text{direct}}\) 个块。
   - 合并、去重后输出最终 top-\(K_{\text{out}}\) 证据块。

### 2.4 关键设计
- **超边（Hyperedge）**：一个事件及其关联的实体集合构成一条潜在超边，在查询时通过 SQL 动态实例化，无需离线预枚举图结构。
- **完备可审计链**：检索全程透明可追溯，每个步骤（实体识别→扩展→SQL连接→合并→排序）均可独立检查，故障可精准定位。

## 3. 实验设计
### 3.1 数据集
选用三个多跳问答基准，推理难度递增：

- **2WikiMultiHopQA**：跨多文档的多跳问题，包含桥接、比较及推理类型。
- **MuSiQue**：通过组合单跳问题构建，最多 4 跳，经反事实过滤确保每步不可跳过，是多跳推理的极限测试集。
每个数据集从开发集随机抽取 1000 个问题，以段落级支持事实注释作为金标准。

### 3.2 对比方法
- **主要对比对象**：**HippoRAG 2**（离线图构建 + 个性化 PageRank 多跳检索），使用与 SAG 相同的底层 LLM 和嵌入模型重新运行，以进行公平对比。

**Recall@K**（K=2,5,10）：至少 1 条支持证据出现在前 K 个返回段落中的查询比例。侧重衡量单步可达性，但在多跳代理检索场景中直接反映上下文效率。

## 6. 主要结论与发现
- **SAG 全面领先**：在 9 个 Recall@K 指标中取得 8 项最优，平均 Recall@2/5 为 79.3%/88.2%，比 HippoRAG 2 高出 11.1/4.9 个百分点。尤其在 MuSiQue 上，Recall@5 达到 **80.0%**，远超 HippoRAG 2 的 65.1%。
- **增益来源明确**：消融实验证明，SAG 的优势并非源于更强的组件（如大模型、大嵌入），而是 **SQL 驱动的结构化扩展** 与 **事件级语义保留** 的协同效果。相比三元组，超边表示进一步压缩了扩展路径损失。
- **双路互补**：结构路径（通过实体连接获得的事件）与语义路径（直接向量召回）高度互补，仅少量结构路径候选就能大幅提升 Recall。
- **扩展的贡献**：查询时扩展主要增加单靠向量难以命中的中间证据，而非改善已召回事件的排序，这对多跳推理至关重要。
- **对嵌入模型的鲁棒性**：SAG 的核心结构增益独立于嵌入模型强度，即使使用较弱的 BGE 嵌入，仍大幅领先强嵌入下的 HippoRAG 2。

## 7. 优点
- **机制创新**：首创将 SQL 作为 RAG 的主检索引擎，用动态超边取代静态图，系统性解决“离线结构与在线召回脱节”难题。
- **架构低维护**：仅需追加写入和字符串规范化，无需全局图重建，天然支持增量更新和水平扩展，具有明确的生产可行性。
- **语义完整性**：“一块一事件”模式保留了原始多实体关联，避免了语义碎片化，同时超边大幅提升了多跳连接效率。
- **透明性与可调试性**：全程可审计的检索链让故障排查变得简单，而非常规端到端黑盒。
- **精巧的资源利用**：SQL 负责精确过滤，向量处理模糊匹配，LLM 仅用于少量高价值排序，各层分工明确，性价比高。

## 8. 不足与局限
- **低频桥接实体的剪枝风险**：当前实体前沿剪枝预算固定（默认 50），在涉及极长实体链或罕见桥接实体的查询（如 2WikiMultiHop 部分样本）中，可能过早截断关键路径，导致尾召回降低（Recall@5 略逊于 HippoRAG 2）。
- **实体合并的轻量化代价**：简单的字符串归一化不进行完整实体消歧，可能将同一实体的不同提及视为不同索引点，削弱跨文档连接密度。
- **实验评估粒度**：仅采用“至少命中一条证据”的 Recall@K，未能严格衡量完整推理链的覆盖度；且未报告答案生成的端到端准确率，对下游效果评估不完整。
- **代理内存更新需求**：当前索引为追加式，不支持对已有事件的更新、冲突或版本管理，距离理想的代理记忆系统尚需扩展。
- **工程细节未明**：缺少硬件配置、批量提取耗时、并发吞吐量等具体数据，限制了可复现性衡量。
