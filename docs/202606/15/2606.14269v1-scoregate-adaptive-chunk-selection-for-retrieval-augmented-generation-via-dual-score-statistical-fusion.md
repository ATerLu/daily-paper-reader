## 摘要
固定基数的检索会不考虑查询复杂性而将固定的前K个文本块注入生成器，导致对于窄查询过度检索，而对于组合查询检索不足。我们描述了ScoreGate，这是一种轻量级的分数空间决策机制，在推理时使用标准流程已产生的两个分数来控制检索基数：双编码器相似度s_i和交叉编码器重排序分数r_i，无需额外的模型推理调用。其核心见解是，交叉编码器的肯定可以挽救由于词汇不匹配而被双编码器检索排名靠后的语义相关文本块——这是固定K或单分数阈值设定未能解决的失败模式。在MS MARCO（200个开发查询）上，ScoreGate实现了MRR@10 = 0.401，保留的文本块比标准Top-K少35%。在内部基准测试（n=300，Fleiss' kappa=0.87）上，ScoreGate在97.77-99.34%的召回率下观察到零假阳性（95% CI [96.4%, 100%]），每个查询的标记数减少34.8%，仅增加31毫秒延迟。在MS MARCO和实际生产流量上的结果表明，自适应检索基数可以在不降低检索质量的情况下提高检索效率。

## Abstract
Fixed-cardinality retrieval injects a constant top-K chunks into the generator regardless of query complexity, causing over-retrieval for narrow queries and under-retrieval for compositional ones. We describe ScoreGate, a lightweight score-space decision mechanism that controls retrieval cardinality at inference time using two scores already produced by the standard pipeline: bi-encoder similarity s_i and cross-encoder reranker score r_i, with no additional model inference calls required. Its core insight is that cross-encoder affirmation can rescue semantically relevant chunks that bi-encoder retrieval ranks poorly due to vocabulary mismatch -- a failure mode unaddressed by fixed-K or single-score thresholding. On MS MARCO (200 dev queries), ScoreGate achieves MRR@10 = 0.401 with 35% fewer retained chunks than Standard Top-K. On an internal benchmark (n=300, Fleiss' kappa=0.87), ScoreGate observed zero false positives (95% CI [96.4%, 100%]) at 97.77-99.34% recall, with 34.8% fewer tokens per query and only 31ms added latency. Results on both MS MARCO and real-world production traffic suggest that adaptive retrieval cardinality can improve retrieval efficiency without degrading retrieval quality.

### 1. 论文的核心问题与整体含义

*   **研究背景**：检索增强生成（RAG）通常使用固定的 Top-K 策略，即无论查询复杂度如何，都取回固定数量的文本块（chunks）送入生成器。
*   **核心问题**：这种“一刀切”的基数控制方式存在根本缺陷。对于简单、导航式查询（如“退款政策是什么”），单个文本块就足够回答，固定 K 值会导致过度检索，引入低相关度的干扰项，增加推理成本和错误率。对于复杂的组合式查询（如“从定价、功能、取消政策等方面比较方案A和B”），又可能因 K 值不足而遗漏关键信息，导致检索不足。
*   **整体含义**：论文提出，最优检索基数应是查询复杂度的函数，而非一个预设常数。通过一种轻量级方法实现自适应检索基数，能在不牺牲（甚至提升）检索质量的同时，显著提高推理效率和降低成本。

### 2. 论文提出的方法论

*   **核心思想：双分数融合与自适应决策**
    *   ScoreGate 并非一种新的检索架构，而是一个可无缝插入现有两阶段 RAG 流程的分数空间决策机制。
    *   **核心洞察**：利用双编码器的语义相似度（s_i）和交叉编码器的相关性分数（r_i）这两个在标准流程中**已经产生**的分数，联合判断文本块的相关性。交叉编码器的“确认”能够挽救那些因词汇不匹配（如使用了同义词、专业术语）而被双编码器检索系统低估的语义相关块。
    *   **零额外推理开销**：整个决策过程不引入任何额外的模型推理调用。

*   **关键技术细节：四区域分数划分与加权融合**
    *   **分数归一化与阈值**：对交叉编码器分数 r_i 进行每个查询的最小-最大归一化。通过离线统计确定两个全局阈值：
        *   \(\tau_s = 0.70\)：双编码器相似度的中位数。
        *   \(\tau_r = 0.08\)：对应约 5% 假阳性率的交叉编码器分数。
    *   **四区域分区**：利用 \(\tau_s, \tau_r\) 将 (s_i, r_i) 分数空间划分为四个非重叠区域：
        *   **B1 (高 s_i，高 r_i)**：无条件保留。双模型均确认相关。
        *   **B4 (低 s_i，低 r_i)**：无条件丢弃。双模型均拒绝。
        *   **B2 (高 s_i，低 r_i)**：冲突区（双编码器认为相关，交叉编码器拒绝），设定高融合阈值 \(\theta_{B2} = 0.255\)。
        *   **B3 (低 s_i，高 r_i)**：关键恢复区（词汇不匹配导致双编码器评分低，但交叉编码器确认相关），设定低融合阈值 \(\theta_{B3} = 0.15\)。
    *   **加权融合分数**：对处在 B2 和 B3 区域的文本块，计算加权融合分数进行二次判断：
        *   \(f_i = \alpha \cdot s_i + (1-\alpha) \cdot r_i\)，其中 \(\alpha = 0.3\)。
        *   该不对称权重（交叉编码器占 70%）的设计依据是：交叉编码器是直接在人工相关性标注上训练的，其分数比双编码器的余弦相似度更能反映“答案级”的相关性。
    *   **基数上限**：为防止上下文窗口溢出，保留的块集 \(C'\) 受 MAX-K 上限（论文中设为 10）限制。若触发上限，则保留融合分数 \(f_i\) 最高的 K 个块。

*   **算法流程**：
    1.  给定已重排序的候选集 \(C\) 及每块的 (s_i, r_i) 分数对。
    2.  遍历每块，根据其落入的区域（B1/B2/B3/B4）应用保留/丢弃规则。
    3.  对保留的块集，按融合分数 \(f_i\) 降序排列。
    4.  输出排名靠前且不超过 MAX-K 的块作为最终送入生成器的上下文。

*   **质量与效率的平衡**：ScoreGate 在 MS MARCO 上以**减少 35-39% 的文本块**，实现了 MRR@10=0.401，优于标准 Top-K（0.387）。在内部基准上，以**减少 34.8% 的输入 token**，实现了零假阳性下的高召回率（97.77-99.34%）。

*   **轻量与即插即用**：仅引入 **31ms 延迟**，且无需任何额外模型训练或推理，可直接集成到现有流程中。

*   **极低的实现成本和实用性**：完全基于现有分数的计算，无需模型微调、不增加任何 API 调用成本，具备极高的工程实用性。
*   **精准解决关键痛点**：四区域设计巧妙地利用了交叉编码器的优势，专门解决了双编码器检索中顽固的“词汇不匹配”问题，这是单靠 Ranking 或简单阈值难以处理的。

### 8. 不足与局限

*   **对上游检索的依赖性**：ScoreGate 无法弥补双编码器检索阶段的低召回问题。如果相关块在初始 Top-N 候选人中根本不存在，方法会直接失效。
*   **评估领域单一**：尽管在 MS MARCO 上做了迁移，但仅包含一个公共数据集。缺乏在更多样化、更专业的领域（如法律、生物医学、金融）以及多语言环境下的验证。
*   **阈值需要按域校准**：虽然推导流程是域无关的，但 \(\tau_s, \tau_r\) 等具体数值取决于模型对和语料的分数分布，应用到新领域时仍需执行离线校准步骤。
*   **未评估复杂查询类型**：论文明确提到，该方法在需要跨段落综合信息的多跳推理（Multi-hop）查询（如 HotpotQA 数据集）上的表现是**未知的**，这是一个重要的应用局限。
*   **内部基准偏差风险**：ARB 数据集的知识库与阈值调优集存在重叠，虽然查询是分离的，但其结果更偏向于“部署内验证”，而非独立的泛化证明。
