## 摘要
搜索智能体的检索仍遵循非智能体信息检索的范式：检索器对语料库排序，智能体阅读一小部分返回的文档。最近的直接语料库交互（DCI）工作表明，智能体可以通过 grep 和文件读取等 shell 工具与原始语料库进行交互。但无限制的交互无法扩展：每个宽泛的 shell 命令都需要扫描整个语料库，延迟随语料库增长而急剧恶化。我们认为，智能体搜索中的检索作用不仅在于选择适合 LLM 上下文窗口的文档，还在于构建一个交互空间：即智能体能够借助相关工具进行探索的语料库有界子集。由此得出两个设计推论：该空间需要由检索提供边界，且其中的对象应经过处理以便交互。作为概念验证，我们提出 RISE（检索交互空间）：使用 BM25 构建交互空间，同时在索引阶段对文档进行处理以支持 shell 式导航。在 BrowseComp-Plus 上，RISE 使用 gpt-5.4-mini 以约四分之一的单次查询成本，达到了与纯 shell DCI 基线相当的 78% 准确率。在百万文档规模下，RISE-BM25 在 gpt-5.4-mini 上达到 81% 准确率，而 DCI 在 gpt-5.4-nano 上下降至 60%，且 100 次运行中有 33 次因超时而失败。

## Abstract
Retrieval for search agents is still inherited from non-agentic information retrieval: a retriever ranks the corpus and the agent reads a small set of returned documents. Recent direct corpus interaction (DCI) work shows that agents can instead interact with the raw corpus through shell tools such as grep and file reads. But unbounded interaction does not scale: every broad shell command is a scan over the whole corpus, and latency degrades sharply as the corpus grows. We argue that the role of retrieval for agentic search is not just to select documents that fit in the LLM context window, but to construct an interaction space: a bounded subset of the corpus the agent can explore with associated tools. Two design consequences follow. The space needs a boundary supplied by retrieval, and the objects within it should be processed for interaction. As a proof of concept, we propose RISE (Retrieving Interaction SpacE): we use BM25 to construct the interaction space; meanwhile, its documents are processed during indexing for shell-style navigation. On BrowseComp-Plus, RISE matches the pure-shell DCI baseline at 78% accuracy with gpt-5.4-mini at roughly one quarter of the per-query cost. At 1M documents, RISE-BM25 reaches 81% on gpt-5.4-mini, whereas DCI on gpt-5.4-nano degrades to 60% with 33 of 100 wall-clock failures.

## 核心问题与整体含义
- **研究动机**：当前面向搜索智能体的检索继承了传统“检索–阅读”范式，即检索器返回少量文档或片段，智能体在上下文窗口内阅读。这种模式限制了智能体与原始语料的深层交互。
- **背景**：直接语料交互（DCI）允许智能体通过 shell 工具（如 grep、read）直接探索完整语料，增强了交互自由度，但面临严重扩展性问题——每条宽泛的 shell 命令都需扫描整个语料，随语料规模增长，延迟和成本急剧上升，准确率显著下降。
- **核心问题**：检索在智能体搜索中应扮演什么角色？能否既保留语料交互的深度，又避免无界交互的规模瓶颈？
- **整体含义**：论文提出将检索的目标从“选择适合上下文窗口的文档”转变为“构造交互空间”——一个有界的语料子集，智能体可借助工具重新探索。这一转变对检索系统的设计提出了两个原则性要求：交互空间需要由检索提供边界，且其中的对象应预处理以支持高效的 shell 式导航。

## 方法论
### 核心思想
- 检索的输出不应是送入上下文的片段，而应是一个持久、可被 shell 工具重新遍历的文件系统工作区。
- 通过 **边界（boundary）** 和 **可导航对象（navigable objects）** 两个设计后果实现。

### 关键技术细节
1. **边界提供：RISE-BM25**
   - 使用 BM25 进行多查询检索，智能体通过 `search(queries)` 工具发出一组自然语言子查询。
   - 每个子查询检索 top‑K（默认 K=1000）文档，所有命中文档的并集被**硬链接（hardlink）**到一个独立的工作目录，该目录在对话过程中单调增长，位于模型上下文窗口之外。
   - 智能体随后使用 `bash`（可运行 rg、grep、cat 等）和行范围读取 `read` 工具在工作区内进行验证和导航。
   - 该设计**明确排除了**：全语料 shell 访问（DCI）、上下文窗口片段（传统 RAG）以及不可重遍历的隐式排序列表。

2. **对象可导航化：RISE 完整版**
   - 在索引阶段离线对文档进行**原位结构元数据注入**，生成一份增强版文档，其中包含：
     - 一个由语言模型生成的行号**目录（Table of Contents）**，每项标注行范围和简短摘要。
     - 在正文中插入 `##` 标记的章节锚点，使 shell 工具可直接跳转到子文档证据区域，而不必通读全文。
   - 处理流程：先用轻量模型（如 gpt-5.4-nano）产生 JSON 格式的章节提议（标题、前若干词作为锚点、描述），再通过精确子串匹配验证锚点并插入 TOC 与锚点标记。原文正文**不摘要、不删除、不改写**，保证事实核查的准确性。
   - 推理时，智能体首先读取前置元数据和 TOC，根据线索选择相关章节，再通过 `read(path, offset, limit)` 精确读取对应行范围，避免全文扫描。

### 算法流程概述
- 查询到来 → 智能体多次调用 `search`，用 BM25 汇集相关文档到工作区。
- 若使用 RISE 完整版，工作区中的文档已被预处理为 TOC‑增强格式。
- 智能体交替使用 `bash` 和行范围 `read` 在工作区内搜索、定位、验证事实，直至生成最终答案。

## 实验设计
- **数据集与场景**
  - 使用 BrowseComp‑Plus（一个用于深度搜索智能体的固定语料评测基准）。
  - 从发布的问答集中采样 **100 个查询** 作为评测。
  - 语料规模设置：
    - **100k**：原始 BrowseComp‑Plus 语料。
    - **1M**：在 100k 基础上加入 900k 条固定种子的 FineWeb‑Edu 干扰文档。
- **对比方法**
  - **RISE**：完整版（BM25 边界 + 离线 TOC 处理）。
  - **RISE‑BM25**：边界版（仅 BM25 工作区，无 TOC 预处理）。
  - **Retrieval‑agent**：复现 BrowseComp‑Plus 基线，使用 BM25（k=5）、512‑token 片段和 `get_document` 工具。
  - **DCI**：直接语料交互，全语料文件系统 + shell 工具（bash、read），采用其原始提示与上下文管理策略。
- **智能体模型**
  - 三种主流模型：Xiaomi mimo‑v2.5‑pro、OpenAI gpt‑5.4‑mini（中等推理强度）、gpt‑5.4‑nano（高推理强度）。
  - 另用 gpt‑5.4（全尺寸，中等推理强度）作为 RISE 接口的上界探测。
- **评判方式**
  - 采用与 BrowseComp‑Plus 一致的 LLM‑as‑judge 协议，以 gpt‑5.1 作为评判模型。
  - 指标：准确率、无答案数量、平均工具调用数、单查询成本（美元）、证据覆盖诊断（gold_R 与 cov_mean）。
- **预算与停止条件**
  - RISE、RISE‑BM25 和 retrieval‑agent：最多 100 次模型调用，每查询 1 小时墙钟上限。
  - DCI：继承其原始配置，最多 300 次模型调用，每查询 1.5 小时墙钟上限（故意给予更宽松预算）。
  - Shell 输出截断及读取限制均按各系统定义设置。

## 主要结论与发现
- **效率‑效能优势**：RISE 在 gpt‑5.4‑mini 上以约 **0.28 美元/查询** 达到 78% 准确率，与 DCI 基线持平，但成本仅为后者的 **四分之一**（DCI 需 1.10 美元/查询）。在更强模型（mimo‑v2.5‑pro）上，RISE 亦以更低成本获得最佳准确率。
- **规模鲁棒性**：当语料从 100k 扩充至 1M，RISE‑BM25 在 3 款模型上均稳定甚至略升（如 mini 上从 77% 升至 81%），而 DCI 在 nano 上从 71% 跌至 60%，且出现 33/100 的墙钟超时失败。
- **边界贡献**：消融显示，仅引入有界工作区（RISE‑BM25）就已取得大部分提升；额外的文档预处理带来 1‑4 个百分点的进一步改善。
- **交互模式验证**：案例表明，智能体成功利用多查询搜索汇聚证据，并在工作区内用 grep/read 进行精确验证；当文档被 TOC 增强后，智能体可直接跳转到致谢等特定章节，减少无效阅读。

## 优点
- **范式创新**：明确将检索输出定义为“可重探索的交互空间”，为设计检索接口和语料处理开辟了新维度。
- **概念清晰**：通过两个具体设计后果（边界、可导航对象）将抽象理念落地，排他性描述强化了方法边界。
- **验证扎实**：在真实深度搜索基准上，覆盖多种模型与成本维度，展示了该框架在效率、成本、可扩展性方面的优势。
- **消融与分析**：边界版与完整版的对比、K 值消融、证据覆盖诊断，均有助理解各组件贡献。
- **可复现性**：提供代码链接，详细阐述预处理流程和提示词，实践指导性强。

## 不足与局限
- **边界检索器单一**：仅使用 BM25，未尝试稠密检索、混合检索等替代方案，也未探究不同检索器对交互空间质量的影响。
- **文档预处理受限**：TOC 预处理仅在 100k 语料上实施，1M 实验局限于 RISE‑BM25，未证明该机制在大规模干扰文档下的效益。
- **评测范围较窄**：仅基于 BrowseComp‑Plus 一个基准的 100 条查询，结论的泛化性有待更多领域和查询类型的验证。
- **评判偏差风险**：评判模型 gpt‑5.1 与使用的智能体模型共享提供商，可能带来偏好性；且小样本下准确率差异（如 2‑3 点）的统计显著性未报告。
- **模型依赖**：智能体和预处理均依赖闭源大模型，离线预处理成本虽低，但仍依赖 API，对于超大规模语料或需频繁更新的场景存在工程挑战。
- **多样性未覆盖**：未探索更复杂的原位元数据方案（如层次图、段落级锚点），也未测试在多语言或非结构化程度更高的语料上的适用性。
